# Factory Droid Desktop

Unofficial Factory Desktop port for **Arch Linux / Omarchy, x86_64**.
Not affiliated with, endorsed by, or supported by Factory.

| Component | Pinned version |
|---|---|
| Factory Desktop payload | 0.206.0 |
| Linux Electron | 42.11.15 |
| Bundled Droid CLI | 0.249.0 |

## Features

- Isolated Desktop profile, separate from your standalone Droid CLI.
- Optional Omarchy theme and Glassy tint integration.
- First-login computer registration and local relay recovery.
- Usage collector and optional [Omarchy service plugin](omarchy/factory-usage-service/).

Remote control, callback registration and the plugin are never enabled automatically.
The personal usage panel is not included.

## Build and install

Requires Arch-based x86_64, system Node/npm, build tools and working user
namespaces (`unshare -Ur true`). Do not run `makepkg` as root.

```bash
sudo pacman -S --needed git base-devel nodejs npm libsecret python librsvg desktop-file-utils
git clone https://github.com/ash-eriga/factory-droid-desktop.git
cd factory-droid-desktop
npm run package:sources
SRCDEST="$PWD/build" makepkg -si
factory-droid-desktop
```

`npm run package:sources` builds the port's own source archive and checks
it against the checksum the recipe pins. The build runs from that archive
and never from the checkout, so the GitHub build and the AUR build ship
the same bytes. The archive needs no dependency of its own: Node, `tar`
and `gzip` are enough. The maintainer's mode additionally uses `git`.

Repository access is required while it is private. The build downloads the
official Windows installer as data, verifies its pinned SHA-256, applies
Linux patches and rebuilds keytar for Linux Electron. The Windows installer
is never executed. **The vendor publisher signature is not verified.**

Use `makepkg -s` instead to build without installing. Generated payloads
and packages are not published by this repository.

The package is not published on the AUR yet; use the GitHub build above.
The AUR recipe is prepared: it is the same `PKGBUILD` and the same
`.SRCINFO` as this repository, and it downloads the same archive from the
release `v0.206.0-14`. That release and its asset do not exist yet, so
the AUR path cannot be used before the release is published, and the
AUR's own rules and license review are still open.

### One recipe, one archive

`PKGBUILD` is the single recipe: it declares the source archive, its
pinned SHA-256, and the build, check and package steps that run inside
the extracted sources. `.SRCINFO` is the metadata makepkg itself writes
for it, and it is checked in.

The source archive is built from the port's own source inventory, with
sorted paths, zeroed timestamps, fixed modes and a gzip stream without a
timestamp, so the same tree always produces the same bytes. It holds the
port's own sources only: no vendor payload, no generated output, no
personal material, and no recipe file, because a checksum inside the
recipe cannot cover the recipe itself.

The inventory (`packaging/source-inventory.json`) is checked in and names
every source file of the port and the mode it ships with. The archive is
therefore built from checked-in data and not from a directory walk, which
is why the same command works in a clone, in a source ZIP, in a release
download and in an AUR checkout: none of them carries a git index. The
command refuses a source file the inventory does not name, a source file
the tree does not hold, and any path that traverses, that is absolute,
that is a link or a special file, or that carries a payload, a credential
or personal material. An artifact of a working tree is never a source: a
log, a dump, a core file, profiler output and generated bytecode are
ignored in a tree, and a source may not name one of them.

A maintainer who changes a source regenerates the inventory, the pinned
checksum and the metadata with:

```bash
npm run package:sources:update
```

That is the only mode that writes to the recipe. The default mode never
rewrites the checksum on a user's machine: a mismatch is reported, and
the build stops. The update is a transaction: if it fails, the
inventory, the recipe and the metadata keep the bytes and the modes they
had, the archive that was still pending is removed, and no archive is
published.

## Usage

```bash
factory-droid-desktop
factory-usage                     # usage JSON
factory-callback register         # optional browser sign-in callback
factory-callback rollback         # restore previous callback associations
```

Enable **Follow Omarchy theme** in Settings → Appearance if wanted.
Desktop state lives under `~/.local/share/factory-droid-desktop/`;
the standalone CLI's `~/.factory/` profile is not migrated.

### Recover a deleted computer

If you removed this PC from your account, Settings → Droid Computers
offers **Register this computer** instead of leaving its card missing.
Registration does not enable Remote Control. Explicitly enabling Remote
Control also verifies and repairs the registration before starting the
relay. Opening the settings page alone does not repair a stale, deleted
registration.

### Upgrading from factory-desktop-arch

The new package replaces the old package but does not migrate its profile.

#### The handover, in order

The new callback helper cannot undo a registration made by the old helper:

1. Before removing or replacing the old package, run `factory-callback rollback`.
2. Install the new package: `sudo pacman -U <package-file>`.
3. Optionally run `factory-callback register` again.

### Uninstall

Quit the app first. If you registered the callback, roll it back before removal:

```bash
factory-callback rollback         # only if previously registered
sudo pacman -R factory-droid-desktop
```

Removal preserves Desktop data and the standalone Droid CLI.
No credential or keyring deletion is performed.

## Development and validation

```bash
npm ci --ignore-scripts --no-audit --no-fund
npm run build
npm run verify
npm test
```

Build before testing to create the pristine vendor snapshot; without it,
upstream-dependent tests explicitly skip. Builds do not install or launch
the Desktop GUI. Existing bundles are reused only when their recipe matches.

`npm run package:sources` builds the source archive the recipe consumes
and checks it against the pinned checksum; `npm run package:sources:update`
refreshes the source inventory, that checksum and `.SRCINFO` after an
intentional source change. A source file that was never added to the
inventory is refused rather than shipped, so a new source has to be added
before the archive is regenerated.

The 0.206.0 port passed independent review and a build from a fresh GitHub
clone with empty dependency/runtime caches, Arch's system Node/npm and
normal dependency checks. All 218 automated tests passed with no skips.
The resulting package was installed, its installed files verified, and
the application window opened successfully. Browser-to-app sign-in was
subsequently confirmed manually after explicit callback registration.
Full GUI behavior and cross-device remote control remain unverified.
Release-version alignment does not guarantee macOS/Windows feature parity.

The unified packaging added twenty-eight tests to the suite (246 in total,
no skips). They cover the deterministic source archive, the refusal of an
undeclared file and of a tampered checksum, the maintainer's mode and its
refusal of an untracked or a forbidden source, the default mode running
in a source tree without a git index, the AUR layout exercised with
makepkg up to the extraction of the sources, and the guards of the
archive: a listed or tracked personal artifact, a source tree that is a
link, an environment that would change the bytes of the archive (an
override, a shell startup file or an exported shell function), a
maintainer's update that fails and leaves the recipe, the metadata and
the inventory exactly as they were, and a rollback that cannot finish
without leaving a pending archive behind. The suite runs without git:
the archive is built from the inventory, and the maintainer's mode says
so when there is no checkout to read. Both layouts subsequently completed
full makepkg builds with 246 tests passing and no skips, using verified
local source archives and public download caches. Public release-asset
retrieval and installation of the new packaging remain separate checks.

Deleted-computer recovery adds eight regression tests. They exercise the
actual patched registration, preload and renderer with synthetic services,
including an explicit repair after a backend 404, the missing-card action,
and registration failure without enabling the relay. These are not a
claim of authenticated Remote Control recovery on a real account.
